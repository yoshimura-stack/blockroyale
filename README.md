# BLOCK ROYALE v0.39 RC2 — 50人・Free向け検証版

この版は、50人の実機テストへ進むための候補版です。**実際のSupabase Freeで50人対戦を保証する段階ではありません。** 旧版の背景・HUD・ライン消去演出・投下通知・ゲームエンジンを引き継ぎ、通信と勝敗管理を変更しています。

本番と同じSupabaseを使うため、新しい `br39` 領域と `BLOCK-TEST-039` 部屋で検証します。旧版の `matches / players / player_states / attacks` や設定を変更するSQLは含めていません。ただし、CPU・通信量・無料枠は同じプロジェクトで共有します。本番イベントと同時には検証しないでください。

## 変更点

- 50人全員へのRealtime配信を廃止。対戦中は約1秒ごとに状態・攻撃・確認応答を1回にまとめます。通信完了後に次を送るため、回線が遅いと間隔は長くなります。
- 参加者一覧は約3秒ごと、相手の盤面は必要な最大4人分だけ取得します。HOST / PROJECTORは約2秒ごとです。
- 攻撃の到着には通常0〜約1秒＋通信時間の遅れがあります。受け取った後の「あと2ターン」などのルールは維持します。
- DBがK.O.順位・優勝者を確定します。1試合の優勝者は最大1人。全員が通信切断で失格なら優勝者なしです。ほぼ同時のK.O.はサーバーの受理順で順位が付きます。
- 送信番号と攻撃IDを使い、応答が失われても同じ攻撃を二重に送らない仕組みにしました。
- 45秒間、正常な新しい通信がない参加者は失格。判定は残っている画面の次の通信時に行います（定期処理は最大約5秒間隔、全画面を閉じた場合は再接続時）。
- HOSTは主催者アカウントでログイン。PLAYERは主催者が配る入室コードと名前だけで参加します。
- **HOSTのF5は試合を維持します。全員を消すときはEMERGENCY RESET。** 50人イベント中の誤リセットを防ぐための変更です。
- **PLAYERの試合中F5はその試合を失格扱いにします。** 盤面を失った状態で有利に復帰することを防ぎます。通信が一時的に切れるだけなら同じタブで自動再試行します。次の試合には参加できます。
- 1280px前後のPCで左右パネルが隠れる旧CSSの競合と、ライン演出CSSの改行不備を修正しました。

## 初回の導入

RC1導入済みの場合は [RC2更新手順](UPDATE_v039_RC2.md) を参照してください。新規環境ではRC1のSQLの後にRC2の追加SQLを適用してください。公開ファイルは `public/` 配下です。

1. 現在動いている旧版ZIP・Cloudflareの公開版を残します。今回のZIPは、まず別のプレビューURLまたは別の静的サイトへ置いてください。フォルダ単位で更新し、旧JSとの混在を避けます。
2. 本番イベントが動いていない時間に、Supabase SQL Editorで `supabase/migrations/20260917033647_free50.sql` を実行します。追加専用のSQLです。旧版のSQLを再実行する必要はありません。
3. Supabase AuthenticationのUsersで、HOST専用のメール・パスワードを持つユーザーを用意します。ユーザーのUUIDを控え、`supabase/SETUP_HOST.sql` のプレースホルダーをそのUUIDに置き換えて実行します。既存の主催者用ユーザーがあれば再利用できます。パスワードやservice_roleキーをHTMLに書かないでください。
4. 新しいURLのHOSTを開き、上記アカウントでログインします。12〜160文字の推測されにくい入室コードを決め、「部屋を新規作成」を押します。このボタンは既存部屋の入室コードを変更しません。
5. PLAYERを開き、同じ入室コードと名前でREADY。PROJECTORにも同じ入室コードを入力します。
6. 2人以上がREADYになったらBATTLE START。8秒の予告後に開始します。対戦前10秒以上通信がない人が残っていると開始できません。元のタブで復帰してもらうか、RESETして全員入り直してください。

部屋名を変更する場合は `public/js/config.js` の `ROOM_CODE` を全員共通の値にし、その部屋をHOSTから新規作成します。旧版とは通信方式が異なるため、旧版PLAYERと新版HOSTは一緒に使えません。

## 5人 → 20人 → 50人の実機検証

まず5人で下記の機能確認を行い、問題がなければ20人・50人へ増やします。各人数で10〜15分、最後は50人で2試合連続を推奨します。全員がPCのゲームタブを手前に出し、スリープを避けてください。

| 確認 | 合格の目安 |
|---|---|
| 入室 | HOSTのREADYが実人数と一致。1人1タブ |
| 開始 | 全員がカウントダウンから開始。開始の取りこぼしなし |
| 攻撃 | 投下が重複しない。小さい半透明通知の後ろでミノが見える |
| 通信 | 再試行表示が継続しない。参加者操作に対して画面が固まらない |
| 終了 | WINNERは1人。敗者の名前・スコア・順位は本人のもの。PROJECTORと一致 |
| HOST F5 | 対戦・参加者・結果を維持 |
| 一時的な切断 | 10秒程度の切断後、同じタブで復旧。攻撃の重複なし |
| 長い切断 | 1人を45秒以上切断し、残りの画面が失格として扱う |
| NEXT BATTLE | 接続中の参加者は再入力せずREADYへ戻る。盤面・スコア・攻撃を初期化 |
| EMERGENCY RESET | 全PLAYERが入室画面、HOST一覧は空、PROJECTORはLOBBY |

Supabase側では検証前後のUsage（Egress）、DB負荷、APIエラー・応答時間を記録してください。ローカル測定をFreeサーバーの性能保証として扱わないでください。反応が遅い・再試行が続く場合は人数を増やさず、その人数と時刻を記録します。

任意の自動テストは `tools/LOAD_TEST.md` を参照してください。50人の実機操作・社内Wi-Fi・端末描画の確認の代わりにはなりません。

## 無料枠の見積もり

2026-09-17確認の公式資料では、FreeのRealtimeは100メッセージ/秒、非キャッシュEgressは月5GBです。新版はRealtimeを使用しないため、その配信上限を回避します。一方でDB APIの応答もEgressを消費し、DB処理能力やネットワーク遅延の制約は残ります。

50人の模擬RPCテストの応答本文からは、約0.32GB/時相当でした。これは短時間・ローカル・英数字の短い名前・ほぼ空の盤面による参考値です。実際の名前、攻撃数、HTTP処理、圧縮、接続時間、他サービスの利用で変わるため、最初は**50人で1時間あたり0.3〜0.8GB程度の計画枠**を取り、実機検証後にUsage実測で置き換えてください。無料枠を確約する数値ではありません。イベント後はHOST / PROJECTOR / PLAYERを閉じて通信を止めます。

- https://supabase.com/docs/guides/realtime/limits
- https://supabase.com/docs/guides/platform/manage-your-usage/egress

## 検証済み・未検証

`VALIDATION_v039.md` に詳細があります。ローカルDBの整合性・権限テスト、クライアント試験、2人のブラウザ操作、50模擬クライアントのRPC試験を行いました。本番SupabaseへのSQL反映・実際のAuthアカウントでのログイン・Freeでの50人負荷・50台の描画はまだ実行していません。

スコア・攻撃量・盤面の計算は従来どおりプレイヤー側です。サーバーで全ゲームを再現する不正対策は含みません。社内の信頼できる参加者向けの設計です。旧版の公開テーブル権限は変更しておらず、新版の主催者認証が旧版を保護するわけではありません。旧版を廃止する時点で旧APIの権限を整理してください。

## 元に戻す場合

新版の全画面を閉じ、保存してある旧版の静的ファイルへ戻します。旧版データは今回のSQLでは変更されません。新しいbr39領域は削除しなくても旧版へ戻せます。検証データを消すときは新版HOSTから対象部屋をRESETしてください。
